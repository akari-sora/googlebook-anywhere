# Compatibility (Googlebook Anywhere v0.3.0)

This document describes which machines the Googlebook Anywhere v0.3.0 image
can be installed on, the current support level for each model, and what has
**not yet been verified on real hardware**.

- The only machine verified on real hardware is an **Alder Lake-P engineering
  sample** of the Acer Chromebook Spin 714 (codename KANO) — iGPU `8086:46a6`.
- All other KANO SKUs and all other x86-64 machines have **not been run on real
  hardware**; their status is always marked "expected to work, untested".
- This document only covers image-level compatibility. For firmware flashing,
  writing the USB, and safety trade-offs, see `FIRMWARE.md`, `SAFETY.md`, and
  `HOW-IT-WORKS.md`.

> 中文版：`COMPATIBILITY.md`.

The v0.3.0 16658739 pins and Microdroid IFMA pins do not establish hardware acceptance; see the [verification record](VERIFICATION-v0.3.0.md). Hardware results below are from earlier images.

### Why did v0.2.0 only work on one machine?

v0.2.0's GPU allowed only a single iGPU ID (`xe.force_probe=46a6`). The iGPUs of
other KANO SKUs (`46a8`, `46b3`, `a7a1`, `a7a9`, …) were rejected by
`xe_pci_probe()` with `-ENODEV`, and lapis ships no fallback DRM/fbdev driver, so
the result was a **black or frozen screen**. Audio (`8086:51c8` → `sof-adl.ri`)
still initialized in the background, but the user could not see anything.

### What changed in v0.2.1

v0.2.1 expands `xe.force_probe` in `profiles/kano/profile.toml` from a single ID
to **12 iGPU PCI IDs** (covering ADL-P/U and RPL-U, including single-channel
memory variants, with `46a6` first and **no** wildcard `*`). The ADL-P IDs are
defined in the kernel's `drivers/gpu/drm/xe/xe_pci.c` (`adl_p_desc`) and
`include/drm/intel/pciids.h`.

An earlier image was tested on this engineering sample; v0.2.1 not yet tested on hardware.
v0.2.1 has **not been verified on any real hardware yet** — it is expected to fix
the black-screen SKUs above, but this needs on-device confirmation.

### 13th-gen (CP714-2WN, codename Zydron) audio

The 13th-gen `CP714-2WN` shares the `KANO` board and `Google_Kano.*` firmware,
but its audio uses the Raptor Lake (RPL) topology: it needs
`intel/sof/community/sof-rpl.ri` and
`intel/sof-tplg/sof-rpl-max98373-nau8825.tplg`. **Untested.**

## Other x86-64 machines (`generic-x86`, experimental)

For x86-64 UEFI machines (for example AMD) whose GPU has no driver in the
Googlebook kernel. The CPU must meet "Minimum CPU" below (Intel 12th gen or AMD Zen 5 and newer).

- Output goes through the firmware **GOP framebuffer**; drawing is done on the
  CPU (**SwiftShader** software rendering).
- **No GPU acceleration**; it is slow, and resolution is determined by firmware.
- **Verified only in QEMU, never booted on a physical PC.**
- Requires UEFI boot from USB and **Secure Boot disabled** (the image has no
  Secure Boot signature).
- Features that need machine firmware, such as Wi-Fi and audio, generally do not
  work; the usable range is whatever `install/gbos-probe.sh` reports.

## Minimum CPU: expected Intel 12th gen or AMD Zen 5 and newer (not tested)

On 2026-10-17 the lapis base (ramdisk first-stage `/init`, `/system` and `/vendor` `bin` and `lib64`, and 44 APEXes; 2,865 ELF files) was disassembled:

- Many libraries contain **AVX2 / FMA / BMI (x86-64-v3)** code (media codecs, TFLite, ML libraries; about 720,000
  instructions in total).
- Some contain **GFNI**, **AVX-VNNI**, **SHA-NI**, **256-bit VAES / VPCLMULQDQ**, **AVX-512** and **AVX-VNNI-INT8** (libcrypto, libyuv, ML, audio and
  camera libraries).
- The build precisely patches 17 host ELF targets: the original 16 plus `system_ext_a/bin/trusty_security_vm_launcher`. Older evidence called the Microdroid guest the 17th site, so the Trusty coordinator is site 18 in that historical numbering; the actual PATCHED-target total is 17.

Much of this runs without a CPU check: first-stage `/init` itself uses x86-64-v3, GFNI, AVX-VNNI and SHA-NI directly;
`libcrypto` always takes SHA-NI and, without AVX-512, always takes 256-bit VAES / VPCLMULQDQ; zlib's adler32 checks
only SSSE3 and then executes AVX-VNNI. AVX-512 in `libcrypto` is behind a runtime check (confirmed by disassembly);
the other AVX-512 uses (41 files in total, for example ML, audio and camera libraries and `libjxl`) and AVX-VNNI-INT8 are presumed to be behind runtime checks (KANO lacks both and works on hardware).

Only KANO (Intel 12th gen Alder Lake-P) has been verified on hardware. The AMD HX 370 (Zen 5) has never run on real
hardware; a Ryzen AI 5 PRO 340 (also Zen 5) was measured to have all of these instructions except AVX-IFMA and AVX-VNNI-INT8 (`avx_vnni=1 avx_ifma=0 avx512ifma=1 sha_ni=1 gfni=1 vaes=1 vpclmulqdq=1 avx_vnni_int8=0`; for AVX-IFMA see the
last point).

- The earlier statement "AVX only, Sandy Bridge or newer" was **wrong** and is withdrawn.
- **Expected to work**: Intel 12th gen (Alder Lake) and newer, AMD Zen 5 and newer.
- **Expected to fail** at boot with illegal instructions (SIGILL): Intel 11th gen and older (no VEX-encoded AVX-VNNI;
  the 6th–10th gen Skylake family and older Core CPUs also lack SHA-NI and GFNI), and AMD Zen 4 and older (Zen 4 has
  AVX-512 VNNI but not VEX-encoded AVX-VNNI). This is inferred; this project has not tested those CPUs. The third-party
  project gbOS86 reports the same on an Intel 8th gen (i5-8365U): `/init` executes SHA-NI at boot and zlib executes
  AVX-VNNI; it only boots by trapping illegal instructions in the kernel and emulating them in software (slower). This
  project does not do that.
- **Known risk and build-time patch (AVX-IFMA, `[cpu_compat] patch_ifma = true`)**: the patcher checks the SHA-256, executable ELF mapping, context, constant table, and original encoding for 17 targets before applying the 12-byte in-place replacement. The targets are split across `vendor_a` (5), `system_a` (11), and `system_ext_a` (1). Exact APEX signer, payload key/salt, EROFS metadata, and persistent-keyset checks still apply.
  The exact checks include executable `PT_LOAD`/`PF_X` mapping, the 73-byte context and 128-byte table. The replacement is `c4 e3 69 02 5e 10 05 c4 e2 f1 b4 c3` (`vpblendd` + `vpmadd52luq`) → `c5 f1 f4 4e 10 c5 f9 d4 c1 0f 1f 00` (`vpmuludq` + `vpaddq` + nop). The host targets are vendor's `lib64/libzmij.dylib.so`, `bin/ectool` (verified before removal), and USB desktop HAL; system's `libzmij`, `libinput`, `libinputflinger`, `prefetch`, `ectool`, and `aisealhostservice`; virt APEX's `vm`, `virtmgr`, `early_virtmgr`, `crosvm_minimal`, and `crosvm`; audio APEX's `libzmij`; fingerprint APEX's crosfp service; and system_ext's Trusty launcher. The manifest gives their exact paths and hashes.
  Each rebuilt APEX preserves its stock v3 signer minimum/maximum SDK range and approved payload `apex.key`/salt. Stock input may contain the known optional SourceStamp block while its v2/v3 signatures are independently verified; rebuilt output rejects that old block. Every other ZIP entry, including `stamp-cert-sha256`, retains its original compressed bytes and name/CRC/size/order. That retained metadata causes an expected missing-SourceStamp warning in ordinary apksigner verification; no SourceStamp authenticity is claimed. System, system_ext and APEX readback compares logical inode metadata and raw supported xattrs, including capabilities, plus UUID, build time, pcluster, superblock feature bits and volume name. Physical inode layout, compression placement and inline/shared xattr encoding may change. The APEX keyset defaults to `$(dirname "$GBOS_AVB_KEY")/apex-keys`; the installer defaults to `$WORK/keys/apex-keys`, and explicit `GBOS_APEX_KEYS_DIR` overrides either. Back it up with the AVB key: losing it changes the next build's APEX identity; Android 17 keep-data behavior still needs on-device verification. Build information records public payload-key SPKI DER and container-certificate DER SHA-256 fingerprints.
  The scanner never deletes a raw VEX candidate. The manifest classifies the complete set as 17 patched targets, 29 `known_non_instructions` (`product_a` 17, `system_a` 1, `vendor_a` 2, and 3 each in `boot_a`, `boot_b`, and `efi_system_a`), 9 residuals, and 1 `unsupported_allowlist` object. Every non-instruction and residual pins the partition, typed container chain, target SHA-256 (plus container-layer hashes where specified), file offset, and `encoding_hex`/instruction encoding. Disassembly or `.gnu.hash` evidence affects classification only; it cannot remove a candidate from the report.
  The nine host-kernel pins cover three sites in three byte-identical placements: the `boot_a` and `boot_b` kernel payloads and ESP `kernel.efi`. Their decoded vmlinux SHA-256 is `f8ede4cc42dc65707dea5c281eb6d4f89f3b15a510c51f61fe5f5afbc44cddd5`.   A missing or changed candidate pin stops the build. The scanner recognizes xz, gzip, zstd, lz4, zip, newc, EROFS, ext4, Android sparse, AVB0, and bzImage through the union of known magic and image suffixes (including a decoded payload's inner logical suffix after stripping trailing `!<kind>`/`:<kind>` markers and one matching `.gz`/`.gzip`, `.xz`, `.zst`/`.zstd`, or `.lz4` suffix per decoding layer, falling back to stripping one generic compression suffix when the outer filename extension does not match the actual compression magic); a match through either route must open completely, and an unopenable or over-depth nested container stops the build. Matching Linux `lib/decompress_inflate.c:__gunzip`, gzip is decoded via header flags (`FHCRC`/`FEXTRA`/`FNAME`/`FCOMMENT`) and raw deflate (including flushing buffered output at input EOF for `>64 KiB` streams without an 8-byte trailer) while skipping the 8-byte trailer without failing on CRC/ISIZE mismatch or a missing/truncated trailer after a valid `Z_STREAM_END` (raw deflate corruption remains a hard error); legacy LZ4 (`0x184C2102`) follows Linux `lib/decompress_unlz4.c:unlz4()` chunk rules without requiring a prior decoded chunk (a chunk size word equal to `0x184C2102` skips 4 bytes and continues decoding into the same member and output payload, a `0` chunk size word or `<4`-byte trailing fragment ends the member at that boundary regardless of whether any chunk was decoded—making an empty `02 21 4c 18` stream a valid `0`-byte `data` member and handing any `<4`-byte trailing fragment and subsequent bytes to the outer initramfs loop so all-NUL is padding and any non-NUL byte is refused with an unpinnable `non-zero initramfs tail` `ScanError`—and chunks with `0 < size <= 8,421,520` (`LZ4_compressBound(8 MiB)`) are streamed directly to a scratch file without keeping all chunks in RAM, decoded in a single `lz4 -dc` batch pass—including valid multi-chunk streams whose total decoded output exceeds `8 MiB`, which is safe without a pre-batch fast-path check because the `lz4` CLI's legacy decoder (`programs/lz4io.c:LZ4IO_decodeLegacyStream`) enforces the `8 MiB` (`LEGACY_BLOCKSIZE`) per-chunk output cap on each chunk itself while the scanner's post-batch `batch_size <= len(chunks) * 8 MiB` (`LEGACY_LZ4_BLOCK_MAX_OUTPUT`) check is only a defense-in-depth sanity bound—and bisected in `O(log N)` subprocess calls on batch failure to isolate the first failing chunk; for a zero-gap next member immediately after at least one decoded legacy chunk, headers whose 4-byte little-endian value exceeds `8,421,520` (`cpio-newc`, `xz`, `zstd`, modern `lz4` frame `0x184D2204`, or `gzip` with `FLG != 0`) bound the legacy member and are scanned as the next member, whereas a zero-gap `gzip` with `FLG == 0`—whose header `1f 8b 08 00` decodes as little-endian size `559,903 <= 8,421,520`—is decoded as an LZ4 chunk when at least `559,903` bytes follow and fails closed as an unpinnable hard `ScanError` like the kernel, and is scanned as a `gzip` member only when the declared `559,903`-byte block is truncated, as a conservative fail-closed superset of the kernel's in-memory `unlz4()` out-of-bounds read residual; any other non-magic chunk size `> 8,421,520` scans the output decoded so far and stops with an unpinnable hard `ScanError`, any truncated or corrupt chunk after earlier output scans the earlier chunks and stops with an unpinnable hard `ScanError`, and any `0`-output failed legacy LZ4 followed by a non-NUL byte is likewise an unpinnable hard `ScanError`); `zstd`, modern LZ4 frames (`0x184D2204`), and legacy LZ4 subprocesses stream CLI output over a pipe (draining `stderr` concurrently with a bounded tail and a scaled timeout of `30s + 1s per 4 MiB` of input that stays armed across `stdout` reading, `stderr` thread draining, and `wait()` until the child has exited and been reaped, without false timeouts when the child exits right at the deadline), and when a `zstd` or modern LZ4 frame fails the scanner frames complete non-final block prefixes with a clean end marker in `_write_terminated_block_prefix` (always bisecting on the return code `returncode == 0` of the end-marked prefix to locate the first failing block, without depending on `stderr` wording; for `zstd`, `_write_terminated_block_prefix` clears `Single_Segment_flag`, `Frame_Content_Size`, and the content checksum flag and, only when the original frame is single-segment, sets a `128 MiB` window byte `0x88` (other frames keep their original `Window_Descriptor`), so `>128 MiB` single-segment frames whose later blocks reference history beyond `128 MiB` may salvage fewer blocks as a residual while the failed frame stays an unpinnable hard `ScanError`) and also probes the raw prefix through the first failing block to keep the longest decoded output (`prefix_out > destination`) so all bytes up to the last complete block before the first failing block are scanned and any hits in those blocks are reported; in direct initramfs-member context (`vendor_ramdisk_entry` or `boot_ramdisk` roots, or a nearest file node whose leaf name is lower-cased first and the compression suffix is stripped after that by `_is_initramfs_filename` (`.gz`/`.gzip`/`.xz`/`.zst`/`.zstd`/`.lz4`, `.cpio`, and `.img`), then matches the `INITRAMFS_FILE_PREFIXES` `ramdisk*`/`initrd*`/`microdroid_initrd*`/`vendor_ramdisk*`, and its `initramfs_tail`/`sparse_payload` descendants—never applied partition-wide across `boot_*`/`init_boot_*`/`vendor_boot_*`/`standalone_initrd_*` to files like `kernel`/`Image.gz`, and never applied to compressed regular files inside a `cpio_member` such as `.ko.xz`, `.ko.gz`, firmware `.bin.zst`/`.bin.lz4`, or `.txt.gz`; any compressed frame or newc member that produces `> 0` decoded bytes before failing has its partial decoded output scanned first (reporting any unpinned forbidden instruction hit) and then stops with an unpinnable hard `ScanError`; any modern `zstd`/`lz4` frame (top level, nested, or initramfs tail) that fails to decode for any reason, including a content checksum or content size error, is an unpinnable hard `ScanError` whatever the decoder wrote: bytes it did write are scanned for the error message only (naming IFMA hits), a diagnostic scan that stops early on any exception (including `LZMAError`/`zlib.error`/`EOFError` from a ZIP member) is named in the error and never turned into acceptance, and no unsupported pin applies; a modern `zstd`/`lz4` decoder that is missing or cannot start is the same unpinnable hard `ScanError` (only legacy LZ4 without an `lz4` tool stays an `lz4 unavailable` unsupported image that needs an exact pin); an undecodable ZIP/APEX member is recorded as damaged (bytes already copied out of it are scanned first), never stops the scan of the members after it, and then stops the build with an error no pin can accept; only a failed `gzip`/`xz` frame that produces `0` decoded bytes or a failed legacy LZ4 chunk call that wrote no bytes can take the `ImageOpenError` unsupported path (a failed legacy LZ4 call that did write bytes has them scanned first and then stops with an unpinnable hard `ScanError`). The kernel `decompress_method()` 2-byte compressed magics (bzip2 `42 5a`, LZMA-alone `5d 00`, LZO `89 4c`, legacy gzip `1f 9e`) plus Android boot `ANDROID!` and vendor boot `VNDRBOOT` apply to every file and ZIP member after leading NULs (taking precedence over later container checks) and are explicitly unsupported (recording `unsupported <kind> at 0x...` as the reason), proceeding only with an exact unsupported pin (`0` on the pinned base; a base change whose ordinary data starts with one of those 2-byte prefixes after leading NULs requires an exact unsupported pin). Initramfs input follows Linux kernel syntax: 4-byte alignment applies only to raw `cpio-newc` (where a complete entry sequence without `TRAILER!!!` is also accepted when ending at EOF, before NUL padding, or before a compressed member), while after any number of leading NULs a supported compressed frame is opened and walked with an `initramfs_tail` (`offset:0x...`) node in its `container_chain`. The boundary rules are: (1) an unbounded/truncated stream (`length is None`) at offset 0 (`position == 0`), after a prior member (`saw_member`), or at `position > 0` when any non-NUL byte follows the invalid frame header, (2) any failed frame after a real member (`saw_member`), (3) non-NUL bytes after a failed frame when those bytes are not a valid following initramfs member (or any non-NUL byte after a `0`-output failed legacy LZ4 stream), (4) a corrupt `cpio-newc` archive (at offset 0 or after aligned NULs) or a decoded initramfs member that does not end in the `cpio-newc` `Reset` state, and (5) any frame that decoded `> 0` bytes before failing, and any modern `zstd`/`lz4` frame that failed to decode, are all unpinnable hard `ScanError`s; only when `not saw_member` and `0` decoded bytes were produced (and the failed frame is not a modern `zstd`/`lz4` frame, i.e. it is `gzip`, `xz`, or legacy LZ4) can a failed frame take the `ImageOpenError` unsupported path: (a) a structurally bounded (`length is not None`) `0`-output failed non-legacy frame at `position == 0` (or after leading NULs at `position > 0` when followed by a valid initramfs member) is pinnable at frame level by that frame's exact SHA-256 and `container_chain` (including `initramfs_tail` `offset:0x...` when `position > 0`) while every following member is still decoded and scanned (whereas non-NUL trailing bytes that are not a valid following member still fail closed with an unpinnable `ScanError`), and (b) when `position > 0`, `not saw_member`, `0` decoded bytes were produced, and either a bounded failed frame reaches EOF / is followed only by NUL bytes or an unbounded (`length is None`) failed frame has only NUL bytes after its frame header (`_stream_tail_is_all_nul`), it joins the six unsupported magics on the outer-object `ImageOpenError` unsupported path, pinned by full outer-object SHA-256 and `container_chain` (with the frame kind and real offset `0x...` recorded in the reason). A trailing `#BOOTCONFIG\n` footer is stripped only on outer objects (never on the decoded payload of a compressed member) and is excluded only after size, checksum, and whole-body ASCII-text/terminal-NUL-padding validation; a forged footer cannot hide a binary archive. An ordinary file with neither known container magic nor an image suffix is treated as data. Each executable `PF_X PT_LOAD` is scanned at the 4096-byte page granularity used by the x86_64 kernel and bionic: the start is `floor(p_offset / 4096) * 4096`, and the exclusive end is `ceil((p_offset + p_filesz) / 4096) * 4096`, clamped to file size; when clamped at EOF, up to 4 zero bytes are synthesized after EOF for the boundary window without reading past EOF or extending into the next unmapped page. Boundaries where page-rounded ranges touch are included while an end already on a page boundary does not add the following page, and the scanner refuses two `PF_X` mappings whose page-rounded VA ranges overlap with different file deltas as well as any `PF_X PT_LOAD` with `p_filesz == 0` and a non-page-aligned `p_offset` (0 of each in the pinned-base census). A read-only superset census of bionic's `_extend_load_segment_vma` boundary (without filtering on `p_memsz == p_filesz`, extending file-backed RX ranges to `min(max(p_align, 4096), 65536)` and to the next segment's page/offset start, preserving the 1..4 byte synthetic zero-fill window on the new last page when an extended mapping is clamped at an unaligned EOF, and scanning every new VA seam where an extended RX mapping touches the next RX mapping with a different file delta) found 3,478 x86 ELFs with `p_align > 4096` (3,467 top-level `x86_elf` plus 11 embedded) and 1,537 carrying `.note.android.pad_segment` (1,532 top-level plus 5 embedded; 1,535 with both `p_align > 4096` and `.note.android.pad_segment`: 1,531 top-level plus 4 embedded); scanning the extended file ranges (including the unaligned-EOF zero-fill window) and new VA seams (0 seam pairs) found zero new raw IFMA candidates across all 1,535 (and across all 4,301 top-level `x86_elf` objects), while the production scanner retains the 4096-byte page model as its boundary. A one-off K4 audit validated 62 x86 ELFs across 14 parent objects (40 from F7 `x86_elf` parents, 10 actual ELFs that `bsdtar` listed in the single `cidata.iso` parent that F7 classified as data, and 12 from container parents; each `desktop_trusty_*signed.elf` contains 15) and counted and listed 28 rejected non-zero-offset headers (26 rejected with `section_runs_past_eof` inside three `vendor_a` `apex_payload.img` images whose real filesystem members are scanned after container extraction, plus 2 bad-ident coincidences in `classes.dex` and the `adservices` payload), finding zero IFMA candidates and zero errors across all 62 under the same 4096-byte page rules. This K4 result and full audit apply only to the pinned base image with SHA-256 `1a12506eade16e6025b83659b717b7d6ee830e9d1b6447248afcb48cc365370c` (alongside the builder's `lapis CL3B.260622.271.R1` / build `16452207` fingerprint and vendor/system/system_ext EROFS UUID gates); Trusty TAs and the `cidata.iso` guest userland are covered by the one-time audit only (each build scans only outer ELF `PF_X` pages), nonzero-offset embedded-ELF carving and ISO traversal remain outside the production scanner (the complete wrapper materialized 203,559 ZIP members and took 624.94 seconds, about 1.94 times the F7 audit's 321.491 seconds), and both K4 and the full read-only audit must be rerun whenever the base image changes. Each build scans the rebuilt `vendor_a`, `system_a`, and `system_ext_a` trees and their APEX payloads. A separate read-only full-image audit reconciled the pinned base's 55 candidate identities (the prior 46 plus nine host-kernel placement identities), but it is not a claim that every build scans the complete GPT. Static/offline evidence is not runtime or hardware proof. Because `vm.supported=1`, a non-protected Microdroid path remains possible, and the guest formatter can still SIGILL if it reaches the retained instruction. Keep-data APEX identity continuity, a real off-mode full-image A/B comparison, and byte-for-byte reproducibility across two builds still lack hardware or paired-build proof. The current manifest is the authoritative classification.
  Pinnable allowlist (v0.3.0): an exact `unsupported_allowlist` pin can only accept content of which no byte was ever decoded: an unknown or unsupported image kind identified by magic (such as AVB0 vbmeta), the nesting-depth limit, a missing erofs/sparse/ext4 tool or an image that tool refuses with no output written, a 0-output gzip/xz frame after leading NULs that is followed only by NULs, legacy LZ4 under the 0-output rule, a ZIP whose central directory cannot be parsed, and a bzImage whose payload was never decoded (no HdrS header, a payload start outside the file, or a payload_length past end of file whose remaining bytes decode to nothing - if they decode, they are scanned and the build stops unpinnably - or an unknown payload magic; also a zstd/LZ4-frame payload when the host has no decoder for it). The never-pinnable formats (LZO, legacy LZ4) win over "payload_length past end of file and nothing decodable": such a payload still stops the build and no pin can accept it. A legacy LZ4 bzImage payload follows Linux `unlz4()` (a later magic continues the same stream; a 0-size chunk or fewer than 4 bytes left ends it) and is never pinnable: any failure scans what decoded and stops the build. An LZO kernel (`CONFIG_KERNEL_LZO`) is decoded with `lzop -dc` and scanned; without a usable `lzop` it stops the build and no pin can accept it. The bzImage decoders are bounded (timeout 30 s plus 1 s per 4 MiB, 512 MiB output); hitting a bound scans what was produced and stops the build. A bzImage payload that produced any byte and then failed a checksum/CRC or trailing-data check is also scanned first and then stops the build with an error no pin can accept; gzip follows the kernel's `__gunzip`, so a CRC32/ISIZE mismatch is not an error and the payload is decoded and scanned. Once content was decoded or partly decoded (a bzImage with trailing bytes after its decoded payload, a `.ko.gz`/`.ko.xz`/`.ko.zst` that decodes to non-ELF, a ZIP with a member that cannot be read), the scanner scans the decoded bytes first (IFMA hits are reported first) and then stops the build with an error no pin can accept; any other unexpected exception also stops the build and never crashes the scanner.

## `amd-hx370` (experimental, never run on real hardware)

- This is an **experimental** profile for AMD machines and has **never been run
  on real hardware**.
- It provides two boot entries:
  - **default "safe"**: does not load `amdgpu`.
  - **"native amdgpu (experimental)"**: loads the native `amdgpu`. This profile ships a rebuilt gralloc with `backend_amdgpu` (sha256 pinned in `[gralloc]`), and it has still never been run on hardware. This entry may show a black screen; choose the safe entry.
- The build needs a self-built kernel (`GBOS_DEV_KERNEL_DIR`), RADV, and a `GBOS_MINIGBM` that `[gralloc]` names with a matching sha256 (`tools/minigbm/build-libminigbm-gralloc.sh`, git repo only), or `build.sh` refuses (as `profiles/amd-hx370/profile.toml` says).
- If the machine has **Secure Boot** enabled: **back up the BitLocker recovery
  key before** changing Secure Boot settings, or you may be unable to decrypt.
- AX210 firmware and HD-audio / Bluetooth module loading added; never tested on hardware.

## Reporting a new machine

To get a new machine supported, run the read-only probe on the target machine
using any Linux USB:

```
install/gbos-probe.sh --out gbos-probe
```

It only reads `/sys` and `/proc`; the result is in `gbos-probe/report.txt`.
Attach the report to a report ticket (the GitLab issue template). For the full
new-device bring-up flow, see `NEW-DEVICE.md`.
