# 裝到內建 NVMe（取代原本的系統）

有兩種做法：

- **安裝碟**（`install/make-installer-stick.sh`）：一個檔就包含 Googlebook、XBOOTLDR，以及已經寫好的 ext4 `kano-maint`（檔案擁有者 uid 0）。裡面有 `gbos-install`、它的服務、`gbos-update.py`、安裝程式自己會核對的 pristine 資料、`module-blacklist.txt` 與 `builtin-initcalls.txt`。開機選單沒有普通 Maintenance 殼層。有 Install Googlebook to the internal disk、Update Googlebook on the internal disk (keep data)，以及 Googlebook (internal disk) 與 serial-debug。內建碟只會在選了安裝項、並輸入序號之後才被清掉。讀序號時會載入 NVMe 驅動；確認前不寫入、不掛載、不丟棄。Update mode hashes the stick super after the serial matches, before the target is opened for write. 安裝模式在載入 NVMe 之前雜湊隨身碟 super；更新模式要等序號相符，由 `gbos-update.py` 在打開目標寫入之前才雜湊。這不是「兩種模式都在載入驅動之前核對完 super」。開機後選安裝項目即可，不必再跑 `setup-stick.sh`。
  `install.sh` 再 `write-usb.sh` 寫出的 Googlebook 隨身碟**沒有**這套維護系統，不能拿來裝內建碟。安裝碟是另一個檔。做法見 README 第 4 步與 `install/stick/README.md`。
  維護根目錄仍由 `install/stick/make-maint.sh` 組出來。`fetch` 不加 `--cache` 時只檢查清單、不下載；加上 `--cache` 才抓提交的檔案，大小或 sha256 不符就拒絕。提交的 `maint.pins` 是 Arch Linux Archive 2026/10/01 的 145 個套件，那些檔案不在這個 repo 裡。套件裡沒有 `boot/initramfs-linux.img`，linux 套件也沒有 `modules.dep`。`assemble` 在缺檔時用這份根目錄自己的 `depmod -a` 與 `mkinitcpio` 做出 initramfs；做不出檔，或契約沒過，就不留下目錄。在 Linux 測試主機上，對得上的 2026/10/01 快取已經留下根目錄：核心 `7.2.7-arch1-1`，工具 23 個。那次 assemble 印出的 `boot/initramfs-linux.img` 是 29790865 位元組；之後每次組裝以它自己印出的 initramfs 行為準。`pack` 只有在行程是 uid 0（root，或 fakeroot）而且有 `mke2fs -d`、`mkfs.vfat`、`mcopy` 時，才另外寫出 `kano-maint.img` 與 `xbootldr.img`；那兩份映像不是 `make-installer-stick.sh` 的輸入。
  指令只寫一個普通檔，不開區塊裝置，也不需要 root。成功時印 `minimum_stick_sectors`；預設檔案就是這個磁區數，可以稀疏存放。Googlebook 複製到 LBA 37244880 的代表映像是 54546417 磁區、27927765504 bytes。報 28.0 GB 的隨身碟是 28000000000 bytes（28×10^9），裝得下這份檔。`write-usb.sh` 拒絕比映像檔還小的碟。別的映像用它自己印出的 `minimum_stick_sectors`。放到隨身碟用 `write-usb.sh`（只接受 USB 整顆碟、要輸入序號、寫完回讀，備份 GPT 在碟尾）。不要加 `--keep-data`。
  在 Linux 測試主機上，`tests/stick/qemu-install.py --asis` 對這個檔的開機副本本身核對 sha256（與產出檔相同），以 `snapshot=on` 原樣開機、不改選單或開機參數，跑完 `AS-IS ACCEPTANCE OK (40/40)`；`tests/stick/qemu-install.py --produced` 則在核對交付選單後，將開機副本的 ESP `loader.conf` 預設改指額外的序列埠測試項目（不注入 ext4，也不改來源檔），分開跑完序列埠與負面案例 `STICK INSTALLER TEST OK (98/98)`。來源檔案的 sha256 在兩次測試前後皆與它的 `.sha256` 相同。那不是在真的 KANO 上安裝。
- **harness 遠端安裝**（下面這份紀錄）：開發機透過 ssh 操作維護系統，連隨身碟上的 /data 一起搬過去。這是唯一會把 userdata 複製進內建碟的路。斷電只能靠 `/data` 上的 nonce。安全保證是複製並掛上之後清掉 `kano-autooff.nonce`（一般檔、符號連結或目錄）。目錄在同一個遠端 python3 裡刪除（`os.lstat` 必須是真目錄，`shutil.rmtree.avoids_symlink_attacks` 必須為真，錯誤非 0；檔名不經過文字紀錄）。卸載後再唯讀掛上複查，必須是 ENOENT，然後再卸載。掛載失敗、根目錄列不出來、查找錯誤（errno 不是 ENOENT）、刪不掉、重新掛載、複查或卸載失敗，就以非 0 停止，不再 `resize.f2fs`、`fsck.f2fs`，也不再寫 ESP。只有 ENOENT 算這個名字不存在。任何 lstat 發生 ENOENT 以外的查找錯誤就停止；刪除後及重新掛載後的確認，必須得到 ENOENT，成功查到任何物件也停止。`dd` 完成之後、這次清除成功之前的任何停止（行程被殺掉、斷電、ssh 中斷）都可能留下檔案；清除失敗則不會繼續。清除失敗而停下時，`/mnt/ud` 可能仍掛著；下一次執行會被 `guard_idle` 以 NVMe 仍掛載拒絕。vendor 掃描是縱深防禦，讓 TEST 服務不要留在日常碟上。

> 這份是**開發者在 KANO 上做過一次的操作紀錄**，不是一般使用者可以照抄的安裝程式。它需要：
> 隨身碟上另外裝的「維護 Linux」（不在這個 repo 裡）、harness 用的序號與 IP（`tools/harness/kano-env.sh`），以及用開發者選項
> 建出來的映像（`GBOS_ADB_PUBKEY`、`GBOS_LOADER_EDITOR=yes`、serial-debug 預設；`kano-nvme-update.sh` 與 `kano-ui.sh` 都靠 adb）。

**這會清掉內建碟上的一切**（例如 ChromeOS Flex 與它的使用者資料）。先確定 USB 版本在你的機器上一切正常，並自行備份資料。

流程在 `tools/harness/kano-nvme-install.sh`（需要 `--go` 才會寫入）：

0. 來源是必須設定的 `KANO_NVME_SRC`（隨身碟上那個映像的建置產物目錄）。第一次連到 KANO 之前就核對全部本機輸入
   （initrd、bootconfig、每個開機選項），清碟之前再確認來源和隨身碟 ESP 上的是同一個映像；不符就什麼都不寫。
1. 從隨身碟開一個「放行 NVMe、其他封鎖不變」的維護 Linux（`initcall_blacklist` 與 `module_blacklist` 拿掉 nvme）。
2. 備份目標碟原本的 GPT（開頭與結尾各 1 MiB）到本機，以 SHA-256 確認備份完整，失敗就停止。這只保住分割表，不是使用者資料備份。
3. 防呆與寫入在同一次遠端執行裡完成：目標必須是 `TRAN=nvme`、PCI ID 與序號相符的內建碟，不是維護系統的根目錄碟、沒有掛載、
   沒有 holder；任何一項不符就在寫入前停止。每一步只看這一次執行的結果，不看舊的紀錄。
4. 寫入前先讀即將複製的那段（隨身碟開頭到 XBOOTLDR 之前）。檢查器是 `tools/harness/kano-autooff-image.py`，先比對它在維護系統上的 SHA-256，再要求輸出剛好是一行 `vendor clean`。GPT 名稱用 kernel `utf16_le_to_7bit`（每個 UTF-16LE 單位的低 7 bits，遇到 0 停止；kernel 會把非可列印字元換成 `!`，這個檢查器保留低 7 bits，ASCII 的 `super` 兩邊相同）。恰好一個名稱是 `super`，而且它必須完全落在這段裡；多於一個就拒絕。主表的 `my_lba` 必須是正在讀的 LBA，分割表項必須是 128 bytes。LP geometry 先讀 `super+4096` 的主副本（magic `gDla` 且 SHA-256 相符），主副本壞了才讀 `super+8192` 的備援；兩份都不成立就拒絕，不會當成沒有 vendor。每個 metadata slot 都先主後備（安裝器的 `initrd_nvme` 會留下原本的 `androidboot.slot_suffix`，包含 `_b`）。欄位檢查對齊 Android liblp（`system/core` `fs_mgr/liblp/reader.cpp`，android16-release：major 10、minor 最多 2、header 長度與版本相符、SHA-256、分割屬性遮罩、metadata 不得蓋過第一個 logical sector），並套用 `AdjustMetadataForSlot`：`LP_PARTITION_ATTR_SLOT_SUFFIXED` 在 slot 0 加上 `_a`、slot 1 加上 `_b`，名字放不下或 slot 2 以上仍帶這個旗標就拒絕整份映像，不改讀該 slot 的備援。沒有這個旗標的 slot 2（lapis 的第三份 metadata）維持原名。`LP_PARTITION_ATTR_DISABLED` 的 vendor 略過，和 `CreateLogicalPartitions` 一樣；這個 slot 最後沒有可掃的 vendor 就拒絕。`LP_PARTITION_ATTR_UPDATED` 不拒絕（Virtual A/B 的 COW 不在這次檢查裡，掃的是表上的 extent）。表項超過 4096 筆，或 tables 超過 1 MiB，而這份副本的 checksum 與 liblp 邊界都過，就拒絕整份映像，不改選備援。checksum 壞掉的主副本仍改讀備援。另一個 metadata slot 留著舊的 TEST vendor 也會被拒；要清掉就用 `write-usb.sh` 把隨身碟整段重寫。某一 slot 兩份都壞就拒絕。GPT 主表的 header CRC 與分割表 CRC 都要過，主表壞了才讀備援 GPT。表上至少要有一個可掃的 vendor（`vendor_a` 或 `vendor_b`，未停用且有 extent），否則拒絕。extent 數為 0 是未使用的 slot（lapis super 的 `vendor_b` 就是這樣），略過不讀；有 extent 的才讀，而且必須是 linear、落在 super 裡。EROFS 依 inode mode 判斷目錄，不看 dirent 的 file type。48-bit 根 inode 讀 `rootnid_8b`（`feature_incompat` 的 `0x80`；釘死的 kernel/common `3938c8d97142` `fs/erofs/erofs_fs.h`），METABOX（`0x100`）的 dirent 從 metabox inode 取 inode。不認得的 incompat bit、`dirblkbits`、額外裝置、讀不了的 layout 都拒絕。`etc/kano-autooff.nonce` 與 `etc/init/kano-autooff.rc` 會跟著目錄符號連結解析（有次數上限）；`..` 走出 vendor 根目錄也拒絕。解析到一般檔就拒絕，內建碟一個區塊都不寫。讀取走維護系統上的 `dd`（`--dd /dev/sda --bytes`），檢查程式自己不開那顆裝置。同一套檢查在 `blkdiscard` 前再跑一次。接著確認 `lsblk -no PARTLABEL /dev/sda1` 是 `userdata`，才以 `-o ro` 掛上。f2fs 即使唯讀掛載仍可能把先前的 fsync 補完，這一步不是保證零位元組。只有 `lstat` 的 ENOENT 算沒有 `kano-autooff.nonce`；名字在，或列出根目錄／查找失敗，就拒絕，然後才 `blkdiscard`，把 USB 碟上 Googlebook 的範圍 `dd` 到 NVMe，`cmp` 全段比對。
5. `sgdisk -e`（備份表頭移到碟尾）、刪掉維護系統的分割、userdata 移到碟尾並 `resize.f2fs`、`sgdisk -G` 重新產生所有 GUID
   （避免與隨身碟重複；Android 用 `androidboot.boot_part_uuid` 找自己的碟）。分割表改寫之後、任何檔案系統步驟之前，核心回報的 p1 起始 sector（`/sys/block/nvme0n1/nvme0n1p1/start`）必須等於 `NEW_START`；不符就停止，不再 `resize.f2fs`、`fsck.f2fs`，也不再寫 ESP。userdata 掛上之後清掉 `kano-autooff.nonce`（一般檔、符號連結或目錄；目錄由 python3 刪除，不把檔名交回 shell），卸載後再唯讀掛上複查，必須是 ENOENT，然後再卸載。這一步是這條複製路的安全保證：掛載失敗、根目錄列不出來、查找錯誤（errno 不是 ENOENT）、刪不掉、重新掛載、複查或卸載失敗，就非 0 停止，不再 `resize.f2fs`、`fsck.f2fs`，也不再寫 ESP。只有 ENOENT 算這個名字不存在。任何 lstat 發生 ENOENT 以外的查找錯誤就停止；刪除後及重新掛載後的確認，必須得到 ENOENT，成功查到任何物件也停止。`dd` 完成之後、清除成功之前的任何停止（行程被殺掉、斷電、ssh 中斷）都可能留下檔案。
6. NVMe ESP 的 initrd 改成 NVMe 的 boot_a GUID，開機選項拿掉 `nvme_init` 封鎖；隨身碟的 XBOOTLDR 另放一份
   「internal NVMe」選項。
7. 實機開機驗證：by-name 連結指向 `nvme0n1`、`/data` 在 nvme0n1p1。

之後的更新經 `tools/harness/kano-nvme-update.sh`：推送前與真正推送前各掃一次新映像的 super（同一套檢查，必須印出 `vendor clean`），是 TEST 就拒絕，不開機、不寫入。實際寫區塊的是 `tools/harness/kano-delta-push-nvme.py`，只寫 super、vbmeta_a/b 裡有變動的區塊；userdata、GPT 或其他分割有變動就拒絕。直接呼叫這支推送程式不會掃描 vendor。它寫不了 userdata，也就建不出 `/data/kano-autooff.nonce`。更新不會清 userdata 上已經存在的 nonce。ESP initrd 只換 bootconfig（會先從目標碟讀 boot_a GUID 核對）。

nonce 只寫到已核對身份的 USB 隨身碟 userdata（`install/write-usb.sh` 的 `/dev/disk/by-id/usb-...`），必須是一般檔，用完刪除。不要寫到內建 NVMe 的 `/data`。`install.sh`／`docker-install.sh` 不寫內建碟；它們在建置 USB 映像之前拒絕這個開關。`install/update.sh` 先呼叫 `install.sh`；帶 `--disk` 時接著 `exec sudo install/write-usb.sh --keep-data`，寫的是 USB 隨身碟，不是內建 NVMe。安裝碟 `gbos-install.sh` 的全新安裝不複製隨身碟 userdata（新的 `/data` 開頭 16 MiB 為零）；更新模式呼叫 `gbos-update.py apply`（`guard_ranges` 含 userdata，`rollback` 只改 ESP 選單）。這兩條都不拒絕 TEST vendor，也無法自行武裝斷電。
